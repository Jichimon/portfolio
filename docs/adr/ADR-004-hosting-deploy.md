# ADR-004: Hosting and deploy — Cloudflare Workers, static assets

**Status:** Accepted
**Date:** 2026-08-19
**Context:** Builds on ADR-001 (Astro, static output, no backend), ADR-002 (zero runtime Mermaid/Puppeteer — the build environment needs no headless-browser capability), ADR-003 (two static, filesystem-routed locales). This repository has **no GitHub remote today** — confirmed directly against `.git/config`, 2026-08-19 — and decision 6 (publication: whether one gets added, and under what visibility) is still open, scheduled after this one. This decision therefore weighs candidates on whether they need that remote to exist first.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| **Cloudflare Workers, static assets** | Genuinely free at this scale (100,000 req/day free tier; static-asset requests are free and unlimited, don't count against that quota); no git remote required — `wrangler deploy` works from a local `dist/` folder; per-branch preview URLs since mid-2025; confirmed hierarchical 404 lookup and `_redirects`/`_headers` support (locale-specific 404s work); build logs + deployment history for a real, checkable deploy signal (`T-10`); this is where both Cloudflare's and Astro's own current docs and adapter development are investing forward | Comparatively the newer of Cloudflare's two static-hosting products for this exact use case; Direct-Upload-vs-git-integration compatibility once decision 6 lands is not separately documented as unrestricted, only *not documented as restricted* the way Pages' one-way constraint is — an assumption, not a confirmed fact |
| **Cloudflare Pages** | Same free-tier generosity, same git-less CLI deploy, same confirmed 404/redirects/headers behavior, same preview-URL mechanism, longer track record | Astro's own `@astrojs/cloudflare` adapter **dropped Pages support entirely** in v13 (Astro 6, March 2026) — doesn't block Pages functionally (this project uses no adapter, Pages just serves static files), but is a clear, dated signal of where documentation and tooling investment is *not* going; a Direct-Upload project has a documented one-way constraint — it **cannot later switch to git integration**, a real cost against this project's still-open publication decision |
| **GitHub Pages** | Simple, well-understood, generous soft limits (100 GB/month, 1 GB site) | **Structurally requires a GitHub remote to exist before it can be set up at all** — no CLI/direct-upload path exists. Directly collides with decision 6 being unresolved. Also: only one root-level `404.html` is recognized (confirmed via GitHub's own docs and community reports) — forecloses a locale-specific Spanish 404 page without a client-side workaround. No native PR/branch previews without a third-party Action requiring write permissions |
| **Netlify** | Git-less CLI deploy works today; unlimited deploy previews on the free plan; instant rollback to any prior successful deploy (deeper than Vercel's) | Free tier now runs on a **credit model that has changed twice in under a year** (bandwidth/compute exchange rates adjusted since the Sept 2025 switch) — a real predictability cost distinct from whether today's numbers are enough; per-locale 404 support could not be confirmed either way in research, an open question rather than a known yes |
| **Vercel** | Git-less CLI deploy; unlimited previews; generous Hobby limits (100 GB transfer, 50 domains) | Hobby plan is contractually **"non-commercial, personal use only,"** with Vercel reserving the right to disable a deployment at its discretion — whether a job-search portfolio (solicits employment, sells nothing, runs no ads) counts as "personal" is genuinely ambiguous and was not resolved in research; also the shallowest rollback of the group (previous deployment only, not any prior one) |

## Decision

**We choose: Cloudflare Workers, static assets (`wrangler deploy`, `assets.directory` pointing at the Astro build output, no adapter).**

It is the only candidate with no dependency on decision 6 (unlike GitHub Pages), no unresolved contractual ambiguity for this project's actual purpose (unlike Vercel), no pricing-model volatility (unlike Netlify), and it is where both Cloudflare's and Astro's own current documentation are investing, over its sibling product Cloudflare Pages. Confirmed 404/redirects/headers behavior handles ADR-003's `/es/...` URL shape with no extra configuration — every locale route is already a real file on disk.

**Deploy path for now:** manual, via `wrangler deploy` from a local build — git-remote-independent, matching this repository's current state. **If decision 6 later adds a GitHub remote**, Workers Builds (git-integrated CI/CD, GitHub or GitLab only) can be added on top without re-provisioning the project — this is stated as the current understanding, not independently confirmed as unrestricted the way Pages' one-way Direct-Upload constraint was confirmed; verify before relying on it if that day comes.

## Consequences

- **We gain:** a deploy mechanism usable today, independent of decision 6's outcome; free at this project's scale with no bandwidth ceiling on static content; a real, checkable deploy signal (build logs, deployment history) rather than a locally-green gate mistaken for evidence (`T-10`); correct locale-aware 404 handling with zero extra config.
- **We accept losing:** Cloudflare Pages' longer track record for this exact use case, and the (unverified) assumption that Workers' git-integration path stays open after a Direct-Upload-style start needs confirming later, not assumed now.
- **This creates a dependency on:** a Cloudflare account (the author's existing tooling/workflow already assumes one, per this session's available skill set — a practical fact, not a technical requirement); `wrangler` as a build/deploy-time CLI tool, alongside `mermaid-cli` (TASK 17, one-time/offline only) as the project's now-short list of external tool dependencies.

## Review trigger

If decision 6 lands on a public GitHub remote and Workers Builds' git-integration path turns out to be restricted the same way Pages' Direct-Upload path is, that is the trigger to re-evaluate — at that point the cost of having started on Workers rather than Pages should be re-measured against a fresh project set up with git integration from the start. If Cloudflare's free-tier request limits or static-asset policy change in a way that stops being "genuinely free at this scale," re-run this comparison rather than assume the other four candidates are still positioned the same way.
