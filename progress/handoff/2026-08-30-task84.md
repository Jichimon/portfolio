## The traps

- **The entry's own scoping sentence is wrong, and this is the one thing to settle at the checkpoint.** It says *"`private/`'s shell vector for writing is already covered by the existing `write` boundary, so this item is read-only."* It is not: `private` appears in `boundaries.read` and **not** in `boundaries.write`. Verified — `rm private/glossary.md` also returns `{"allowed":true}`. Whether to widen the item is the author's call, not the agent's; `H-04` governs *reading*, so the read half is unambiguously in scope and the write half is a separate judgment. **Do not silently widen the scope, and do not silently leave the finding unstated.**
- **The read vector is not the write vector, and reusing `WRITES` wholesale will miss it.** `WRITES` is a map of *mutating* commands. `cat`, `head`, `tail`, `less`, `od`, `xxd`, `strings`, `grep`, `sed -n`, `awk`, `diff`, `wc`, `base64`, `cp` (as **source**) all read and none are in it. A roster of reader commands is `P-13`'s shape — prefer deriving from argument position over enumerating binaries, or state plainly why a roster is the honest answer here.
- **`sed` and `cp` are in both directions.** `sed -i` writes and `sed -n 1p` reads; `cp private/x /tmp/y` reads the source and writes the destination. A design that assumes one command is one direction will get these wrong.
- **`commandContexts` already distinguishes data from code** — heredoc bodies and single-quoted spans are data, substitutions are not (`TASK 10`). Reuse it. Writing a second decomposition is the drift `TASK 74` and `TASK 65` already paid for once.
- **`P-14` is not optional here.** This is a rung-1 boundary: run the bypasses, do not just watch the happy path pass. `TASK 86` and `TASK 87` both found that the interesting bypass was a *flag-shaped argument resolving through `..`* — `-/../private/glossary.md` deserves a test on day one, in both slash directions.
- **Documenting this boundary must not trip it.** `check-terms` and the guard's own test file will contain the literal string `private/glossary.md`. That is why the decomposition exists; confirm a documenting command still passes before declaring the fix done.
