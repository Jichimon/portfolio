## What already exists — read this before writing anything

`scripts/guards/lib/path-boundary.mjs`, `destinationArgs` (around line 125):

```js
function destinationArgs(args) {
  for (let i = 0; i < args.length; i++) {
    const a = args[i];
    if (a === '-t' || a === '--target-directory') {
      return args[i + 1] !== undefined ? [args[i + 1]] : [];
    }
    const m = a.match(/^--target-directory=(.*)$/);
    if (m) return [m[1]];
  }
  const positional = args.filter((a) => !a.startsWith('-'));
  return positional.length ? [positional[positional.length - 1]] : [];
}
```

The `-t`/`--target-directory` branches are unaffected by this defect — they take an explicit
next-argument or `=`-value, never a filtered fallback. The bug is only in the last line: it
filters on the argument's **raw** text before any path resolution, exactly the mistake `TASK 86`
just fixed in the `'all'`/`'inplace'` loops (`git log` / `git diff` on this file for that
session's change, once committed, shows the shape).

**`TASK 86`'s fix does not transplant directly — read this before reaching for it.** That fix
deleted the skip and checked *every* argument unconditionally, safe there because `'all'`/
`'inplace'` treat each non-matching argument as an independent candidate. `'dest'`-mode is
different: `cp SOURCE DEST` deliberately does **not** flag `SOURCE` — reading from `resources/`
via `cp resources/x.md /tmp/y.md` must stay `allowed` (this is the exact false-positive `TASK 61`
fixed: before it, `cp` was wrongly in `'all'`-mode and denied reads of its own source). Checking
every argument unconditionally here would silently resurrect that regression.

## A sketched direction, verified by hand but not implemented — the traps this hands you

Traced through by hand (not run against the code — verify before trusting):

**Resolve each candidate *before* deciding whether it looks like a flag, rather than filtering on
raw text.** For each argument, compute `repoRelative(arg, root)` first, then filter on whether
*that resolved value* starts with `-` (not the raw argument):

- `-v` resolves to `-v` (an ordinary flag has nothing to collapse) — still starts with `-`,
  correctly excluded.
- `-/../resources/y.md` resolves to `resources/y.md` once `..` collapses the leading `-` segment
  — no longer starts with `-`, correctly becomes a positional candidate.
- `/tmp/x.md` resolves to `tmp/x.md` (or similar, depending on root) — never started with `-`
  either way.

Traced against both the reproducing case and `TASK 61`'s regression case by hand and both come
out right: `cp /tmp/x.md -/../resources/y.md` → last positional resolves to `resources/y.md`
(fixed); `cp /tmp/x.md resources/y.md -v` → `-v` still excluded, `resources/y.md` still last
(regression avoided). **Not verified:** interaction with `ln`/`install`'s own flag sets, and
whether any real flag value legitimately contains `..` in a way that would wrongly un-flag it —
short options for `cp`/`ln`/`install` don't naturally do this, but check rather than assume
(`P-04`).
