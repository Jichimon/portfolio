## Decisions

- **Every blueprint step ships its own acceptance check** (amendment `A24`). The author pushed on this directly: I had been declaring steps done on my own report, backed by ad-hoc shell I ran once and nobody could re-run. That is `P-11` violated while building the harness that defines it. Guards now land with the artifact they guard instead of in a step-6 batch, and the acceptance bar is identical at every step — the check exists, passes on the real artifact, and has been demonstrated failing.
- **A red gate during construction is correct.** `check-context-budget` failed for two steps because `CLAUDE.md` was still 154 lines, and it named that as the outstanding work until step 4 closed it. A gate that only goes green at the end tells you nothing along the way, which is INC-08's lesson applied to the build.
- **The context budget became a gate step, not a note.** Always-loaded lines are derived from the artifact — a rules file without `paths:` frontmatter loads at launch — so nothing is hardcoded. `CLAUDE.md` 154 → 67, total 359 → 271 against a 320 budget whose rationale is written into `guards.config.json`.
- **`docs/templates/` was deleted, and the reason generalizes.** The author asked why a `templates/` directory existed when the spec and ADR templates lived beside their instances. The real defect was sharper than inconsistent naming: `docs/specs/` was empty only because specs had not been written yet, whereas `docs/templates/` could *never* hold an instance — work-item instances go to `TASKS.md` and `progress/`. It also hid a duplication, since `progress/README.md` already had a log template. Each half went where its instances live, and templates now declare `instances:` so the rule is checked rather than remembered.
- **`evals/cases/` was flattened to `evals/`.** Anticipatory structure with nothing behind it — one template and a README do not need a subdirectory. Same proportionality discipline applied everywhere else.
- **Contracts declare their enforcer, and the gate prints the ratio every run.** Answering "how do we ensure contracts are used, not just declared": `check-contracts` fails a contract that claims `built` while its enforcer is absent, fails one that is neither built nor scheduled, and fails a *stale claim* — an enforcer that lands while the status still names a future step. That last case fired on its own this session when `.claude/settings.json` appeared and the Policy row still read "step 5".
- **The spec template gained a TDD contract.** It had traceability but no sequencing, and its status vocabulary (`passing / planned`) collapsed *not written* and *written and correctly failing* into one word. Now `planned / red / green / gap`, plus `tdd` / `tdd_rationale` / `reproduces` fields. `tdd` lives in the spec rather than being inherited from the work-item type because `T-01` keys on type **and** surface, and only the spec knows which files the behaviors land in.
- **Two mechanisms for every boundary, on purpose.** `settings.json` deny rules cover the file tools and survive `bypassPermissions`; the `PreToolUse` guard covers the shell, which deny patterns cannot reach reliably. Neither alone closes the boundary. `check-settings` asserts every declared boundary has both, and fails any boundary resting on an `ask` rule (`G-03`).
- **One `PreToolUse` entry point, several pure functions.** `PreToolUse` fires per tool call, so separate registrations would mean a process spawn each. Each policy is unit-tested alone; the entry point only dispatches and formats.
- **`git-write` is an allowlist.** git has ~150 subcommands and gains more; a denylist protects exactly what its author enumerated. Ambiguous subcommands (`branch`, `tag`, `remote`, `config`, `stash`) pass only in spellings proven read-only.

## Findings from validating against real state (P-04)

- **`check-rules-registry` caught a false green I had produced by hand.** `00-hard-rules.md` had no `rung` column, so the parser read *origin* as rung — and `H-01`/`H-02`/`H-03` passed **by accident**, because their origins contain the digits in "D2", "D1", "A11". Three rules passing for the wrong reason is worse than five failing.
- **`check-templates` caught a defect in itself.** It reported three false positives against `EC-TEMPLATE.yaml`: a `.yaml` template *is* its own schema, but the guard only looked in frontmatter and fenced blocks. Found by running it, not by reading it.
- **The `git-write` red-path battery caught two real bugs before the guard shipped.** `env git commit` and `nohup git push` escaped entirely — direct wrappers pass their command as arguments, not through `-c`, and only flag-wrappers were handled. And `git tag -l "v*"` was denied: requiring *every* argument to be a known read flag rejected the pattern argument. Both fixed; the rule is now "a list flag must be present and no write flag may be".
- **One test was wrong, not the guard.** `C:/Program Files/Git/bin/git.exe commit` unquoted is two tokens in a real shell and fails there too. The realistic quoted form is denied. Recorded as a passing test with a comment so the gap reads as understood rather than missed.
