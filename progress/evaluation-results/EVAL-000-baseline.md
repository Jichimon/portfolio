> **Mode:** A (retrospective replay)
> **Date:** 2026-08-18 · **Compared against:** nothing. **This is the baseline, not an evaluation.** The Baseline and Previous columns below are deliberately empty; there is no prior scorecard, and inventing a comparison would manufacture a trend out of one data point.
> **Question this answers:** If each of the thirteen transcribed incidents happened again today, would this harness catch it — and is the harness paying for itself yet?
> **enforcement_environment:** policy-controlled
> **permission_mode observed:** `unknown` — for **every** run on disk, scored and unscored alike. This is a capture defect, not a posture. See `GAP-05`.

`permission_mode: "unknown"` is not the same fact as "not `bypassPermissions`". The field exists precisely so an evaluator can refuse to merge runs from different regimes, and right now it cannot discharge that duty for any run in the repository. The runs are scored anyway, because `G-04` pins `disableBypassPermissionsMode: "disable"` in project settings and that pin is checked by the `runtime boundary` gate step — but the scorecard records that the assurance comes from a static setting rather than from the observed header, which is a weaker claim.

## Biases of this run — declared, not disclaimed

**1. Circularity — total, and worse than "the instrument was changed by the work it scores".** The instrument *is* the work it scores. Every artifact in the scored set was built during TASK 5, by the same collaboration this scorecard evaluates. Two cases were authored in the same session as the controls they test: `EC-011` (`INC-12`, the fail-open guard) and `EC-013` (`INC-14`, the deny-everything guard). `EC-013` is the sharpest instance — the incident, the fix, the case and the scoring all happened inside a single session, so the case cannot be said to have caught anything it was not written to describe. Circularity is at its worst exactly where the headline result is, and the headline should be read with that discount applied. What survives the discount is narrower and still worth something: the red-path batteries are executable, and they fail when their control is removed, which is a property of the tests rather than of the author's intentions.

**2. Composition — total.** Every work item in the scored set is harness work. No feature, no content item, no migration and no bugfix outside the harness itself has ever run through this process. The harness has been scored exclusively on itself, on a workload chosen by its own authors, which is the condition under which a process looks best and proves least. The four completed content items in `TASKS.md` predate the harness and did not run through it.

**Neither bias is mitigable at this point in the project's life.** They are recorded so that `EVAL-001` — which should be run over the first non-harness work item — is read as the first evaluation with any external validity, and so nobody plots a line through this point and the next one without noticing that only the second one measures a process operating on work it did not author.

## Verdict

**The harness cannot yet be shown to be paying, and this scorecard does not claim otherwise.**

No work item has completed under it. K1 — the metric it was built to move — has no substrate and no capture mechanism. Every outcome number above is a starting coordinate, not a trend, and two of them are drawn from a workload the harness's own authors chose.

Against that, three things are true and worth the cost so far. Its rung-1 boundaries caught two genuine attempts, one of them through an indirect shell vector. Eight of thirteen controls are proven in red, meaning they have been demonstrated failing when the thing they test is removed — which is the difference between a test and a decoration. And the harness found two rung-1 defects in itself, one of which (`repoRelative` comparing the repository root case-sensitively, so a `C:` versus `c:` drive-letter mismatch left paths unrelativized and matching no boundary at all) had **`H-02` and `H-03` failing open** — the two boundaries protecting published content and the trace itself.

But the honest headline is the shape of the failure, not the count of successes: **the first serious use of the harness's own evaluation path hit a guard that denied 100% of the writes it exists to permit.** That guard's battery was green. Its red paths were all exercised; its green path had never been tested against a real payload shape. That is the third defect in the same family as `INC-12` and `INC-13` — a control that reads correctly, tests green, and does not do what it says — and three instances is a pattern rather than a run of bad luck. The pattern is now named and mechanized in `EC-013`, and the resolver is shared, so the fix reaches every path guard at once.

**Read this file as a starting coordinate with a known systematic bias, not as a result.** The question `EVAL-001` must answer is not whether the slope is positive but whether the known failure modes recur on work the harness did not author.

## Attributions

No KPI carries a `Flat` or `Regressed` verdict, because no comparison exists. What follows attributes the two numbers that are *absent or wrong* rather than flat, since an absent metric is the more serious condition — a flat metric is at least measured.

**K1 is unmeasurable — attributed to `work-item`, which has no iteration-capture step.** Not to "the process needs work". The procedure runs implement→verify passes and records the outcome of the last one; nothing increments a counter across them, so the substrate `contracts.md` §6 names ("the work log's iteration record") does not exist in any template. The fix is a field, not a philosophy.

**L is 0/5 on the delegated path — attributed to hook registration, not to agent behaviour.** `SubagentStart` writes a `run.header`, and `InstructionsLoaded` fires for the orchestrator, but no delegated run in any session has ever emitted an `instructions.loaded` event. This is **LOW ADHERENCE measurement, not low adherence** — and the distinction decides the fix. If the rules are in fact loading into delegated context, the harness is under-observing itself and the remedy is instrumentation; if they are not, `INC-04` is live and unmechanized. **The harness currently cannot tell which**, which is the finding, and it is squarely the condition `architecture.md` §K warns about in the opposite direction: an adherence KPI that cannot be read is no better than one pinned at 100%.

**`G-06`'s termination claim is not upheld by the trace — attributed to the `SubagentStop` hook.** `G-06` states that budget exhaustion "terminates it `FAILED` with `reason: budget_exhausted` and the budget named — never a partial success." Scanning every `termination` object on disk returns **`COMPLETE` in every case, without exception**; `FAILED` and `budget_exhausted` appear nowhere in the trace except inside tool-request patterns from agents searching for them. The delegated run that was in fact terminated by its turn budget is not distinguishable in the trace from one that finished its job. This is `G-06` claiming an enforcement level it has not earned, which `00-hard-rules.md` identifies as worse than an honest lower claim.

**High adherence with a defective control, stated plainly for `EC-013`.** The write-scope guard was followed exactly. Its rung was right, its battery ran, its tests passed. It was still wrong. Per the template's own distinction, that is **HIGH ADHERENCE with a bad outcome, so the CONTENT was wrong** — and the corrective is not more compliance but a testing rule about captured payloads, which is what `EC-013` now encodes.
