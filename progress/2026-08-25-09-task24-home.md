## Decisions taken with the author before the spec was written

- **Published order comes from content, not code.** Rejected: a curated order module in `site/lib/`, because a sixth case study would then need a code edit — criterion 1 forbids exactly that. Rejected: deriving from `type` + `featured` + `period`, because two entries share `2025` and the tie-break would be arbitrary.
- **The stack strip renders the full union, unnormalised.** Rejected: an alias table, which is a roster that goes stale the day a new stack value lands (`P-13`). Stated cost: the general and the specific value both render, where the artboard's curated fifteen showed one.
- **The spec gained a section explaining what `HOME-004` does NOT require**, after the author asked whether it implied new UI/data decoupling for bundle reasons. It does not: the pipeline is already built and enforced, and it runs entirely at build time. Measured on the current build — the home page loads **~3.7 KB** of JavaScript, all of it the theme toggle and the scroll-spy. Recorded because the question is a reasonable one to ask again later.

**B3 — case tile**

Created `site/src/components/home/CaseTile.astro`. Read the extracted bento/tile markup and CSS handoff (`b3-bento-source.txt`) and `Hero.astro` as the sibling pattern reference. No file under `docs/design/canvas/` was opened.

Design decisions:
- One component, one `variant` prop (`'anchor' | 'numbered' | 'full'`), covering the three structural shapes in the source: the anchor tile (wide, tag + display-scale h3 + a scale figure and a right-aligned roles block in the foot), the standard numbered tile (a zero-padded position number, plain-text foot with an optional highlighted line), and the full-width tile (horizontal layout, motif beside a body wrapper). `tile-wide` in the source shares the numbered tile's exact content structure and differs only in its grid span — a container-level concern — so it was not modeled as a fourth variant.
- Ten props, three required (`href`, `title`, `variant`), seven optional (`summaryText`, `tagText`, `positionNumber`, `scaleFigure`, `scaleCaption`, `roleLine`, `highlightLine`). Every optional prop is guarded by an explicit `!== undefined` check; an absent value renders no element, not an empty one — checked individually, so e.g. `highlightLine` can render without `roleLine` and vice versa.
- The decorative motif is a `<slot>`, gated by `Astro.slots.has('default')` rather than always rendering the wrapper the way `Hero.astro`'s absolutely-positioned background div does. `Hero.astro`'s pattern is safe unconditional because its wrapper is `position: absolute` and invisible when empty; this tile's motif sits in normal document flow with a `margin-bottom`, so an always-rendered empty wrapper would leave a visible gap on a motif-less tile. Diverged from the sibling pattern deliberately to satisfy the brief's explicit "a tile with no motif renders no motif," and recording the divergence and its reason here.
- `positionNumber` is a typed `number`; the zero-padded `"01"`/`"02"` display string is derived in the frontmatter (`String(positionNumber).padStart(2, '0')`) rather than pushed onto the caller, since it is presentation formatting of a number, not a hardcoded visible string.
- Class vocabulary: `.case-tile` (block), `.case-tile__motif`/`__tag`/`__num`/`__title`/`__summary`/`__foot`/`__scale`/`__scale-caption`/`__roles`/`__highlight`/`__body` (elements), `.case-tile--anchor`/`--full` (variants) — the numbered shape needed no variant class of its own since it is the base style. The source's shorthand (`tag`, `num`, `foot`, `hi`, `scale`, `roles`) was not carried across, per the brief.
- Token mapping applied throughout: every colour is `var(--color-*)`; fonts are `var(--font-display)`/`var(--font-body)`/`var(--font-mono)`; the one media query uses the literal `1180px`, the sanctioned value matching `--breakpoint-medium`, because a media condition cannot read a custom property.
- Type-ramp matches checked property-by-property against `site/src/styles/tokens.css`, not assumed: `.case-tile__title`'s base state matches `--type-title` (700 17.5px body) exactly, and `.case-tile__summary`'s base state matches `--type-small` (400 13.5px body) exactly — both used via `font: var(--type-*)` plus the extracted line-height/letter-spacing as literal overrides, following `Hero.astro`'s precedent for `--type-thesis`. Five other extracted steps were checked and found **no exact match**, so they stay literal, each with an inline comment naming the mismatch: the tag (10px, default weight — no step is 10px, and `--type-label` is 500 not 400), the position number (11px matches `--type-label`'s size but not its 500 weight), the anchor title (28px matches neither `--type-display-s` 24px nor `--type-display-m` 30px), the foot text (11px vs. `--type-mono`'s 12.5px), and the scale figure (30px matches `--type-display-m`'s size but its weight is 700 against the token's 600).
- No grid-column span (`span 2` / `span 3` in the source, for the anchor and full-width tiles) is set in this component. Spanning columns is meaningless without knowing the container's column count, which changes at the medium breakpoint in the source (3 columns down to 2) — that coordination belongs to the bento container, a separate slice per the brief, not to the tile. Flagging this as a loose end: whoever builds the container needs to apply `grid-column` per `.case-tile--anchor`/`--full` from the container's own stylesheet.
- The full-width tile's own row-to-column flex switch (source: `@media (max-width: 1180px) { .tile-full { flex-direction: column; ... } }`) is intrinsic to the tile itself, independent of the container's column count, so it stayed here as the component's one scoped media query.

**No visible string, no colour literal, no comment referencing anything outside `site/`** — checked against the file as written.

**Files touched:** `site/src/components/home/CaseTile.astro` only. No other file read or written (`b3-bento-source.txt` is outside the repository, in the session scratchpad).

**B4 — contact section**

Created `site/src/components/home/ContactSection.astro`. Read the extracted contact markup/CSS handoff (`b4-contact-source.txt`) and `StackStrip.astro` as the sibling pattern reference. No file under `docs/design/canvas/` was opened.

Design decisions:
- The source's two-column grid (`.contact-layout`: a 520px content column plus a `.testimonials` column) is not carried across at all — per the brief, the testimonials column is out of scope, and the content column is built to occupy the row alone, so no grid wrapper or column-width constraint exists in this file. The 44px-gap responsive rule the source applies to that grid (at what the handoff calls line 398) is therefore moot — there is no second column to collapse — and was not ported.
- Twelve typed props: `heading`, `invite`, `note`, `mailtoAddress`, the three field label/placeholder pairs (`emailLabel`/`emailPlaceholder`, `aboutLabel`/`aboutPlaceholder`, `messageLabel`/`messagePlaceholder`), `submitLabel`, and `links: { name: string; url: string }[]`. None of these names are given verbatim in the brief (it names the props by role, not by identifier), so they were chosen to match the field's purpose and the site's existing naming register.
- `<form action={`mailto:${mailtoAddress}`} method="post">` — the address is never written into this file, only interpolated from the prop, per the brief.
- Renders no result state: no `sending`/`sent`/`error` branch, no `aria-live` region, nothing announcing an outcome — a one-line comment on the form explains why, without naming a path, spec or rule id (`S-08`).
- Every label is a real `<label for="…">` bound to a same-file `<input>`/`<textarea>` `id` (`contact-section-email`, `-about`, `-message`); those ids are static technical identifiers, not visible strings, and are stable because exactly one instance of this component is expected per page.
- Class vocabulary: `.contact-section` (block) with `__heading`/`__invite`/`__form`/`__field`/`__label`/`__input`/`__textarea`/`__submit`/`__footer`/`__note`/`__links`/`__link` elements — the source's shorthand (`invite`, `cf-submit`, `field`) was not carried across, per the brief.
- Token mapping applied exactly per the brief's table: `--color-bg`, `--color-ink`, `--color-ink-muted`, `--color-ink-faint`, `--color-accent`, `--color-border`, `--color-label`; fonts via `--font-display`/`--font-body`/`--font-mono`. Two deviations from the literal source, both noted inline or here:
  - `.contact-section__heading` uses `font: var(--type-display-m)` per the brief's instruction that this step (`600 30px Space Grotesk`) matches that token exactly; the source's additional `letter-spacing: -0.008em` was dropped on the assumption the token shorthand already carries the tracking that step needs, since the brief gave no separate tracking property for it — flagging as a loose end if that assumption is wrong.
  - The source styles the input/textarea underline with `var(--border-strong)`, a token not present in the brief's given mapping (only `--border` → `--color-border` is listed). Mapped it to `--color-border`, the only border token supplied, since the brief said to use the given names and not derive new ones — flagging as a loose end in case a `--color-border-strong` token exists and was simply omitted from the mapping table.
  - All other extracted sizes that do not match the type ramp (16px invite, 11px label, 14.5px input, 14px submit, 11.5px note, 12.5px links) stay literal, per the brief.
- Added `width: 100%; box-sizing: border-box;` to the input/textarea rule, which the extracted CSS snippet does not itself set. Without it these elements fall back to a browser-default intrinsic width once the source's 520px grid-column constraint is gone, which would leave the standalone form visibly too narrow — judged necessary for the brief's "its own layout is correct occupying the row alone, at all three widths" requirement rather than a source-literal property. Flagging as a design addition beyond the extracted snippet, for the orchestrator to confirm against the artboard if it matters.
- The source's link separators (` &middot; ` text between the mailto/GitHub/LinkedIn links) were not reproduced. The links are rendered as a `<ul>`/`<li>` list with flex `gap` for spacing instead of an inline punctuation separator, because no separator character was supplied as a prop and the brief's no-visible-string rule reads most conservatively as "introduce no text content this file doesn't already have a prop for." Flagging as a minor visual deviation from the artboard.
- No breakpoint-scoped media query was added: the section has no two-column layout to collapse, and the existing flex rules (`.contact-section__form`'s column flow, `.contact-section__footer`'s `flex-wrap: wrap`) already hold correctly at `1180px`/`820px`/`560px` without a width-conditional rule, so none was invented.
- No colour literal, no visible string, and no comment referencing anything outside `site/` — checked against the file as written.

## Orchestrator — design-fidelity pass, after the author looked at the page

The author compared the built home page against the design side by side and reported that the
cards matched neither the layout nor the art. They were right on both counts, and on more than
they named. Nothing automated had caught any of it: `astro check`, `check-site`, the smoke tier
and the mutation gate were all green through every one of these.

### What was missing, and why each one was missing

| Gap | Cause |
|---|---|
| **The five per-tile motifs did not exist at all.** `CaseTile` had a slot for one and nothing ever passed one | The slice that owned them was never run. `HOME-007` was `planned` and stayed `planned`; the item was one step from being closed with a critical-adjacent behavior unbuilt |
| **The bento left a hole.** Three columns, four featured tiles at spans 2·1·1·1 — the second row held one tile beside two empty cells | The design resolves it with a `tile-wide` class on its third deep dive. That class belongs to no component's own block, so the per-component extraction never saw it |
| **The year was dropped from four of five tiles.** `outcome ?? period` reads as a fallback and behaves as a filter | The two are only interchangeable when at most one is ever present, which was never true of this content |
| **Three whole responsive stages were absent** — the one-column bento at 820, the anchor tile's smaller heading and stacked foot, the thesis stepping 40 → 30 → 25 | Same cause as the hole: they live in the design's shared media blocks, not inside any component |
| **The contact form ran the full width of the page** — 1032px inputs | The design gives that column a 520px measure as one half of a two-column grid. Dropping the testimonials column was correct; letting the survivor grow into the vacated space was not |

The first, third and fifth were each **predicted in this log before they shipped**. The contact
slice wrote down that it was building no width constraint and flagged it. The prediction was
recorded and then not acted on, which is its own finding: a flagged loose end that no one
converts into work is indistinguishable from one nobody noticed.

### What was built

- `site/lib/layout/bento-spans.mjs` — `fillLastRow(baseSpans, columns)`, test-first, nine tests.
  The last tile of a group grows into whatever its row has left. At today's five case studies it
  reproduces the design exactly; at any other count it closes the gap instead of reproducing a
  decision that no longer applies. **100% mutant-kill, zero survivors.** The first run left one
  alive — `columns < 1` mutated to `<= 1` — which named a real untested case, the single-column
  stage. Killed with a test rather than a suppression.
- `site/src/components/home/work/CaseMotif.astro` — the five motifs, slug-keyed, rendering nothing

- The three missing responsive stages, and the contact column's measure.
