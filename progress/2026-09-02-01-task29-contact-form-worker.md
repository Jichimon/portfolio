## Decisions taken with the author before the spec

**1 · No second Worker. The site's own Worker grows a handler.** `site/wrangler.jsonc` is assets-only today — the file says `NO main` in its own comment. Adding `main` plus `assets.run_worker_first` makes the Worker that already serves the site answer the POST. Rejected: a separate `contact-worker/` package. It would have meant a second `wrangler.jsonc`, a second deploy step, a second secret store, cross-origin CORS on the form, and — the deciding cost — a new **top-level directory**, which matches the `paths:` frontmatter of neither `30-testing.md` nor `50-implementation.md`. A governance gap opened by a directory name is `INC-08`'s shape, and this shape has already fired once here (`TASK 42`).

**2 · `run_worker_first` is declared rather than inferred.** Cloudflare's own docs say both *"if an appropriate static asset is not found, Cloudflare will invoke your Worker script"* and *"`not_found_handling: 404-page` returns a 404 for requests which do not match a static asset"*. Those two sentences do not settle what a POST to an unmatched path does when both a Worker and a 404 page exist. Naming the route explicitly costs one line and removes the question; guessing costs a deploy to find out.

**3 · Rate limit + honeypot, not Turnstile.** The item's own constraint reads *"a Turnstile challenge **or** a rate limit"* — the rate limit satisfies it literally. Turnstile costs a dashboard widget, two more keys, a third-party script on the home page and a bilingual label, for a form with zero traffic. Declared as a residual with a trigger, not as coverage.

**4 · `from` is the site, `reply_to` is the visitor.** The author asked for the visitor's address in `from`. That is not available: SPF/DKIM/DMARC treat it as forgery and Resend only accepts a verified domain. `reply_to` produces the behaviour actually wanted — Reply answers the visitor. Stated once, then built (`P-17`).

**5 · The API key is a Cloudflare Worker Secret.** Not `wrangler.jsonc` (committed, public repo), not the assets (downloaded by the browser), and not a GitHub Actions secret — that last one would work but would put the key through the CI runner on every push for no gain. This is `G-08` and the item's own constraint, met rather than reinterpreted.

**6 · No new test runner, and no new dependency.** Resend is one `fetch`; the SDK buys nothing. `@cloudflare/vitest-pool-workers` would be a **third** runner, and the register already warns that a third deserves the explicit pricing `ADR-006` gave the second Stryker config. The Worker's risk is in payload validation, which is pure and goes in `site/lib/contact/` where `node:test` and Stryker already reach. The handler itself is a thin wrapper — the same category as `scripts/guards/gate/**`, deliberately outside the mutation glob.

### The author's own edit, mid-session, and what it cost

**`site/lib/nav/nav-structure.mjs` changed under the work** — the author commented out the three `reserved` nav slots (`writing`, `architectures`, `search`) so they stop rendering on the published site. Two colocated tests went red immediately, both on `assert.ok(reservedItems.length > 0)`.

That assertion was not ceremony: it is the guard that stops the loop under it from passing over an empty set, which is `T-02`'s own shape one level down. So the tests were right and the data legitimately changed — the honest fix was neither a skip nor a deletion.

**Resolved by folding both into one self-staling test.** While the tier is empty it asserts that the three withheld keys are absent, naming them; restoring one to the data fails that assertion and hands back the shape and contiguity checks underneath it. Same mechanism `pendingRoutes` uses in the guard config, and for the same reason given there — *"that second half is the whole reason this is not a skip list"*. The `reserved` **kind** never lost coverage: a synthetic item already exercises the resolver's branch, which is what `NAV_ITEMS` being empty cannot reach. The commented-out lines also gained the sentence saying why they are out, which they did not have.

### A guard gap found by walking into it (`P-04`)

**`check-site`'s `S-01` scanner blanks `<style>` blocks and not `<script>` blocks.** `astroFileRegions` in `scripts/guards/lib/site-structure/visible-strings.mjs` strips CSS character-for-character and says so in its own comment; `scanTemplate` below it has no script awareness at all, so an inline script's body is walked as a text run and every word in it reads as a visible string.

`BaseLayout.astro` passes only because its script body is wrapped in a bare `{ … }` block, which the scanner reads as an Astro expression and skips. Whether that was intent or luck, it is now the repository's de-facto convention for an inline script, and it is written down nowhere.

The contact wiring follows it — a braced block around a dynamic import, which is also the shape the layout already uses for the theme and the scroll tracking, so this is the established pattern rather than a workaround invented here. **The gap itself is left open and reported rather than fixed inside this item**: it produces a false positive, not a blind spot, so nothing is unguarded while it stands. Trigger for closing it: a component needing an inline script that cannot be brace-wrapped.

**A second, smaller tension found the same way.** `querySelector<HTMLElement>(…)` type-checks and the `S-01` scanner reads `<HTMLElement>` as an HTML tag. Narrowing with `instanceof` instead satisfies both, and is better code regardless: a selector that stops matching returns early instead of carrying an `undefined` into a runtime error.

### One red gate run that was the session's own fault, recorded rather than retried away

A `--profile full` run failed `e2e smoke` in 9.9s on `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` inside `astro build`. **That was not a flake and not a defect in the suite** — a `wrangler dev` process started for the local probe was still alive, watching `site/`, while the build rewrote `site/dist` underneath it.

Worth writing down because the mistake is repeatable: **`wrangler dev` respawns its own child, so it survives a kill aimed at one pid.** Three successive kills each reported success and the port kept answering under a new pid; only killing the parent with the tree flag freed it. The immediately preceding full run had passed the same step in 27.5s, which is what made the environmental cause visible rather than the code.

`T-06` says a flake is a finding. The finding here is about the session, not the repository: nothing was retried until green — the cause was identified, removed, and the run repeated on a machine with no node processes left alive.

### The first real deploy, and the defect it found in this item's own check

**The site is live and the deploy landed whole**: 16 derived routes checked at the deployed origin, all 200. The contact probe reported a finding, which is the probe working — and the finding's *message* was wrong, which is a defect this item shipped.

The endpoint answered **500 `{"error":"not_configured"}`** because the Worker secret had not been set yet. The probe said *"either the route never reached the handler, or the handler accepts anything"*. **Both halves were false**, and a 500 carrying a JSON error body is itself proof that the handler ran. Checked against the deployment rather than reasoned about:

```text
POST /api/contact  ->  500  {"error":"not_configured"}     the handler ran
GET  /api/contact  ->  405  {"error":"method_not_allowed"} the Worker owns the route
GET  /nope         ->  404  text/html                      the 404 page is untouched
```

So `run_worker_first` is confirmed **in production**, which no local run could establish — the one thing the whole arrangement rested on, and the reason it was declared rather than inferred.

**Fixed test-first, as a bugfix** (`T-01`: the failing test must reproduce the bug before the fix). Four cases added, exactly one red: a 500 naming a missing key must report the missing secret and must NOT blame the route. `probeContactEndpoint` now diagnoses from the evidence rather than listing possibilities — 404 is the only status that means the asset router kept the path, 200 the only one that means validation did not run, and a self-describing error body is quoted rather than guessed at. An unreadable body falls through to a generic line instead of turning a wrong status into an exception.

**A check that fails correctly and explains wrongly costs more than one that stays quiet**, because it spends the reader's time in the wrong file. That is the finding worth keeping from this deploy, not the forgotten secret.

**One cross-item consequence, stated rather than left to be discovered:** the deploy job exits 1 on this finding, so `TASK 32`'s own outstanding clause — a green `ci` run end to end — cannot close until the secret is set either. Both items clear on the same action.

**Any brief names this item descriptively — *"the contact form item"* — never by its id.** `extractWorkItems` scans the whole brief text for `TASK <n>`, including inside a quoted error message, and this item is `feature`-typed.
